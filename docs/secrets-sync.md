# Secrets sync with Bitwarden

`secrets-sync` writes `~/.secrets` on each machine from one folder in my personal Bitwarden vault. Bitwarden is the single source of truth: values change there, and each machine pulls only the variables tagged for it. The shell rc files source `~/.secrets` as before.

The program is `scripts/secrets_sync.py`. The installer links the wrapper `home/.local/bin/secrets-sync` onto `PATH`, and the wrapper runs the script with `uv run --script`. The vault is unlocked by hand for each run and locked again at the end of it.

## Storage model

| Bitwarden object | Holds |
|---|---|
| Folder `secrets-sync` in the personal vault | Every item this tool reads or writes |
| One secure note per group, such as `livekit` or `cloudflare-r2` | The variables that belong together |
| A hidden custom field per variable | Field name is the variable name exactly, field value is its value |
| A text custom field `machines` on each item | `all`, one machine tag (`mac`, `bigboss`) or a comma list such as `mac, bigboss` |

The folder lives in the personal vault, not in an ai-coustics organization collection. Personal folders are visible only to me, while a collection is shared with whoever the org grants it to, so a personal key put there by mistake would reach colleagues. The tool enforces this: it ignores items that belong to an organization and refuses to write to them.

Items fail closed. An item without a `machines` field reaches no machine until it has one. Each variable may appear in only one item. Variable names must be upper case, and a field may not set a name that a shell, loader or tool treats as code, a search path, a trust anchor or an API endpoint (`PATH`, `LD_PRELOAD`, `DYLD_*`, `PROMPT_COMMAND`, `LESSOPEN`, `GIT_*`, `UV_*`, `*_PROXY`, `*_BASE_URL` and similar). This denylist limits what an edited vault item can do on every machine, but the vault stays trusted input: an item can still point a variable such as an endpoint URL somewhere else. Values must fit on one line.

The `machines` tag decides what each machine writes to disk. It is not an access boundary: every machine that unlocks the vault downloads and can decrypt all of it, so an attacker on bigboss who captures the master password or a session key gets the Mac-only items too. Tag billing-capable keys (cloud and GPU providers) narrowly so they do not sit in plain text on hosts that do not need them, and use a separate Bitwarden account or Bitwarden Secrets Manager if a host must never be able to read them.

## Files on each machine

| Path | What it is |
|---|---|
| `~/.secrets` | Generated by `pull`, mode 600. A header says edits are overwritten; variables are grouped under a comment naming their Bitwarden item, in sorted order, as `export NAME='value'`. Every variable is exported, including one that a hand-written file only assigned. A delimited local-only block at the end is kept as is. |
| `~/.config/secrets-sync/config.toml` | Made by `secrets-sync init`. Holds this machine's tag and a hash of the machine's hardware or OS id, so a config copied to another host stops working there. |
| `~/.local/state/secrets-sync/backups/` | Mode 700. The previous `~/.secrets` from each pull that changed it, mode 600, newest five kept. Backups keep removed and rotated values until they age out, so delete them after retagging an item away from a machine or rotating a key. |

Variables that should stay on one machine and never reach Bitwarden go between the local-only markers:

```sh
# >>> secrets-sync local-only >>>
export SCRATCH_TOKEN='...'
# <<< secrets-sync local-only <<<
```

A local-only variable wins over a Bitwarden variable of the same name, and `pull` warns about it.

## Commands

| Command | What it does |
|---|---|
| `secrets-sync init --machine mac` | Tags this machine. Run once per machine. |
| `secrets-sync check` | Unlocks, syncs and compares `~/.secrets` with Bitwarden by name. Lists variables missing locally, unmanaged ones (local but not in Bitwarden), ones Bitwarden does not assign to this machine and ones whose values differ. Exit code 1 on drift. Writes nothing. |
| `secrets-sync pull` | Writes `~/.secrets` for this machine's tag, backing up the old file first. Prints the tag and the names it wrote. `--dry-run` prints the names that would change. |
| `secrets-sync push --item NAME --machines TAGS VAR...` | Copies named variables from `~/.secrets` into one Bitwarden item, after a confirmation that lists names only. Refuses to overwrite a field or retag an item without `--force`. |
| `secrets-sync import PLAN.toml` | Runs `push` for each item in a plan file that lists names and tags, never values. |
| `secrets-sync doctor` | Checks without unlocking: bw installed and recent, logged in, locked, last sync age, file and backup modes, git ignore rules, the pre-commit guard, rc sourcing, shell history and crontab. |

`check`, `pull`, `push` and `import` refuse to run without a terminal on stdin and stdout, so cron or a pipe cannot start them by accident. `check` and `pull` accept `--non-interactive` when `BW_SESSION` already holds an unlocked session; they then neither prompt nor lock.

## First-time migration

The Mac and bigboss copies have drifted: bigboss has two variables the Mac lacks, and nobody has compared the values of the shared names. Bitwarden becomes the reference by importing the Mac's file, adding bigboss's extras, then pulling on both.

1. Merge this change and update both machines: `git -C ~/dotfiles pull`, then `uv run --script ~/dotfiles/install.py`. This links `~/.local/bin/secrets-sync` and `~/.config/git/hooks/pre-commit`.
2. Install the Bitwarden CLI. The Mac already has it from `brew install bitwarden-cli`. On bigboss run `brew install bitwarden-cli` if Homebrew is there, otherwise `npm install -g @bitwarden/cli`.
3. On each machine, log in yourself: `bw login` (over `ssh -t bigboss` for the server). If the account is on the EU cloud, first run `bw config server https://vault.bitwarden.eu`. Ignore the `export BW_SESSION=...` hint that `bw login` prints, and run `bw lock`.
4. Tag each machine: `secrets-sync init --machine mac` on the Mac, `secrets-sync init --machine bigboss` on bigboss. Then run `secrets-sync doctor` on both and fix what it reports.
5. On the Mac, write an import plan outside any git repo, for example `~/secrets-import-plan.toml`. It holds names and tags only; the import refuses any other key:

    ```toml
    [livekit]
    machines = "all"
    vars = ["LIVEKIT_API_KEY", "LIVEKIT_API_SECRET", "LIVEKIT_URL"]

    [cloudflare-r2]
    machines = "mac, bigboss"
    vars = ["R2_ACCESS_KEY_ID", "R2_SECRET_ACCESS_KEY"]
    ```

6. On the Mac, run `secrets-sync import ~/secrets-import-plan.toml` and confirm each item.
7. Review the folder in the Bitwarden app: every variable a hidden field, every item with the right `machines` tag. Turn on two-step login for the account if it is not on yet.
8. On bigboss, run `secrets-sync check`. Push the two bigboss-only variables with `secrets-sync push --item <group> --machines <tags> NAME...`. For every name marked `differs`, find out at the provider which key is live and fix the value in the Bitwarden app.
9. On bigboss, run `secrets-sync pull --dry-run`, then `secrets-sync pull`. A hand-written file that still holds variables Bitwarden does not know makes `pull` stop and name them: push them, or rerun with `--keep-unmanaged` to move them into the local-only block.
10. On the Mac, run `secrets-sync pull`. It adds the two variables the Mac lacked.
11. Run `secrets-sync check` on both machines. Each should end with `No drift.`
12. Turn on the commit guard for this repo: `git -C ~/dotfiles config core.hooksPath home/.config/git/hooks`.

## Daily use

To add or change a variable, edit the item in the Bitwarden app (or `secrets-sync push --force` from the machine that has the new value), then run `secrets-sync pull` on each machine that should get it and open a new shell. Shells already open keep the old values. `secrets-sync check` shows whether a machine has fallen behind.

### On bigboss

Run it in an interactive ssh session (`ssh -t bigboss`, then `secrets-sync pull`), because `bw unlock` needs a terminal to ask for the master password. Each run unlocks, syncs, reads and locks again; no session key is cached between runs, and nothing writes the master password or session key to disk. The server holds only the bw CLI's encrypted vault cache (under `~/.config/Bitwarden CLI/`), which is useless without the master password. Do not export `BW_SESSION` there, do not use `bw unlock --passwordenv` or `--passwordfile` and do not schedule `secrets-sync` from cron.

## Rotating a key

1. Create the new key at the provider.
2. Put the new value in the item's hidden field in Bitwarden.
3. Run `secrets-sync pull` on every machine whose tag the item names, then `secrets-sync check`.
4. Restart long-lived processes (tmux panes, notebooks, agents) that read the old value.
5. Revoke the old key at the provider.
6. Delete the backups that hold the old value: `rm ~/.local/state/secrets-sync/backups/secrets.*` on each machine.

`check` lists variables that exist on a machine but not in Bitwarden as `unmanaged`. They never get rotated with the rest, so push them or move them into the local-only block.

## Recovering from a bad pull

Each pull that changes `~/.secrets` first saves the old file. To restore the newest backup:

```sh
ls ~/.local/state/secrets-sync/backups/
install -m 600 ~/.local/state/secrets-sync/backups/secrets.<timestamp> ~/.secrets
```

If Bitwarden itself holds a wrong value, fix it in the app (its item history keeps earlier field values) and pull again.

## Pre-commit guard

`scripts/secrets_commit_guard.py` reads the staged content of every added, modified, renamed or copied file (the whole file, binary files included) and blocks the commit when it:

- adds a file named `.secrets` or `.secrets.*`
- contains the literal value of any variable in the local `~/.secrets` that is 8 or more characters long, whatever the variable is called and in any format
- assigns a non-placeholder value to a secret-like variable name from `~/.secrets`
- matches a known token shape (private key headers, AWS, GitHub, Slack, Google, Hugging Face and Linear keys, `sk-` keys)
- assigns a value of 20 or more characters with high entropy to a secret-like name

A secret-like name contains, as a whole word between underscores or camel-case breaks, `KEY`, `API_KEY`, `SECRET_KEY`, `ACCESS_TOKEN`, `TOKEN`, `SECRET`, `PASSWORD`, `PASSPHRASE`, `PASS`, `PWD`, `CREDENTIAL`, `CREDS`, `AUTH`, `BEARER`, `LICENSE`, `SESSION`, `COOKIE`, `DSN`, `SALT`, `PAT` or a close variant (`SECRETKEY`, `APITOKEN`). The value match means a URL or id stored in `~/.secrets` also blocks a commit that contains it; mark such a line with the pragma below.

The guard keeps `~/.secrets` values in memory only. It prints the file, line number and reason (for a value match, the name of the variable), never the value. Add `secrets-guard: allow` to a line to pass a false positive; the pragma exempts that line from every rule. It fails closed: a staged file it cannot read, or a `~/.secrets` that exists but cannot be read, blocks the commit.

The hook wrapper `home/.config/git/hooks/pre-commit` runs the guard from its own directory with `uv run --no-project --no-config`, with `UV_*` and `PYTHON*` variables removed, so a repository's `uv.toml`, `pyproject.toml`, `.python-version` or direnv settings cannot choose its interpreter or package index. It refuses to run a guard that is missing, not owned by me or writable by group or others.

To run it for this repo only, use step 12 above. To run it in every repo, set `git config --global core.hooksPath ~/.config/git/hooks`. Git then ignores each repo's own `.git/hooks`; the wrapper runs the repo's own `pre-commit` hook after the guard, but other hook types in `.git/hooks` (such as `commit-msg` or `pre-push`) stop running.

`.gitignore` and the global ignore file `home/.config/git/ignore` both list `.secrets` and `.secrets.*`. This repo is public, so it holds no list of variable names: `check` reads names from Bitwarden and the guard reads them from the local `~/.secrets`.

## Threat model

This protects against drift between machines, secrets landing in a git commit, a machine receiving keys it should not hold and leaks through command lines, logs, error messages, temp files and loose file modes. The session key travels to `bw` only in its environment, values go to `bw` only over stdin, `~/.secrets` is replaced by an atomic rename of a mode 600 temp file and every run that unlocked the vault locks it again, including after an error or Ctrl-C.

It does not protect against:

- A compromised account on a machine. Whoever runs as me can read `~/.secrets`, the backups, every shell's environment and the environment of a running `bw` process, and can capture the master password as I type it, which opens the whole vault, including items tagged for other machines.
- Exposure while viewing values in the Bitwarden app: the clipboard, screen sharing and screenshots.
- A weak Bitwarden account. The vault is as safe as the master password and the account's two-step login.
- `git commit --no-verify`, a line carrying the allow pragma and secrets the guard's patterns do not recognize (for example a value split across lines or encoded).
- Values already loaded into running processes after a rotation.
